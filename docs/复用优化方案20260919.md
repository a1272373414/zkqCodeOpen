## 一、核心发现：数据格式完全兼容

原脚本 `doc/decrypt/awcocx_main.lua` 的颜色特征格式：

```lua
findMultiColor(x1, y1, x2, y2, "主色-101010", "dx1|dy1|色1|dx2|dy2|色2|...", 方向, 相似度)
```

zkqCodeOpen 的 `ColorSchema.parse` 格式（`app/src/main/java/com/coc/zkqcode/jar/code/colorschema/ColorSchema.kt`）：

```kotlin
ColorSchema.parse(x1, y1, x2, y2, "主色-101010", "dx1|dy1|色1,dx2|dy2|色2,...", 方向, 相似度, name)
```

**唯一差异**：偏移点之间的分隔符。
- 原脚本：所有字段统一用 `|`
- zkqCodeOpen：点内部用 `|`，点之间用 `,`

转换是纯机械操作：`split("|")` → 每 3 个一组 → 组内保留 `|`，组间用 `,`。

## 六、优化项 5（P2）：坐标归一化工具

### 目标
借鉴 `_prelude.lua` 的 `r()` 函数，为 zkqCodeOpen 增加坐标缩放能力，适配非 1280x720 分辨率。

### 实现
```kotlin
object CoordNormalizer {
    private const val BASE_W = 1280
    private const val BASE_H = 720
    private var scaleX = 1f
    private var scaleY = 1f

    fun init(actualW: Int, actualH: Int) {
        scaleX = actualW.toFloat() / BASE_W
        scaleY = actualH.toFloat() / BASE_H
    }

    fun r(x: Int, y: Int): Pair<Int, Int> =
        Pair((x * scaleX).toInt(), (y * scaleY).toInt())
    
    fun r(x: Int): Int = (x * scaleX).toInt()
}
```

### 落地步骤
1. 在游戏启动时获取实际屏幕分辨率并初始化
2. 逐步将硬编码坐标改为 `CoordNormalizer.r(x, y)`
3. 颜色 schema 的搜索区域也需要归一化

## 九、自动化转换脚本（Python）

```python
import re

def convert_offset_str(original: str) -> str:
    """
    将原脚本 "dx1|dy1|c1|dx2|dy2|c2|..." 转为 zkqCodeOpen "dx1|dy1|c1,dx2|dy2|c2,..."
    """
    parts = original.split("|")
    points = []
    for i in range(0, len(parts) - 2, 3):
        dx, dy, color = parts[i], parts[i+1], parts[i+2]
        points.append(f"{dx}|{dy}|{color}")
    return ",".join(points)

def parse_feature_entry(name: str, entry: list) -> str:
    x1, y1, x2, y2 = entry[0], entry[1], entry[2], entry[3]
    main_color = entry[4]
    offset_str = convert_offset_str(entry[5])
    direction = entry[6]
    similarity = entry[7]
    return f'''val {name} = ColorSchema.parse(
    {x1}, {y1}, {x2}, {y2}, "{main_color}",
    "{offset_str}",
    {direction}, {similarity}, "{name}"
)'''

# 使用示例
# 1. 从 awcocx_main.lua 提取 _ENV["特征"] 表
# 2. 对每个条目调用 parse_feature_entry
# 3. 输出到对应 .kt 文件
```

## 十一、开发前复核结论（2026-09-19）

### 11.1 已复核无误的部分

| 结论 | 复核方式 |
|------|---------|
| 颜色格式两边一致，均为 BGR(0xBBGGRR) 六位十六进制串，`ColorSchema.parse` 会做 BGR→RGB | 把 `函数275a` 的颜色分别按 BGR / RGB 两种解释，到真实 1280x720 截图上做整图找色：BGR 解释下红色系特征有 800+ 像素命中，RGB 解释下几乎为 0 |
| 偏移点分隔符转换规则正确（点内 `|`、点间 `,`） | 与 `ColorSchema.parse` 实现逐行对照 |
| 第一章/第二章/第三章的行号、条目格式、`特征` 表结构描述与原文一致 | 定位到 `awcocx_main.lua` L37843 `_ENV["函数275a"] = function(多点找色界面)`；共解析出 **120** 个界面条目，其中 51 处带兜底变体 |

### 11.2 方案遗漏的关键点：**坐标系不一致（必须处理，否则迁移数据全部错位）**

- 原脚本的坐标是设备**竖屏原始缓冲区 720x1280**：
  - `_ENV["屏幕宽"], _ENV["屏幕高"] = getDisplaySize()`，兜底硬编码 `720 / 1280`（L50543-50544）；
  - 坐标 y 最大到 1279，且 `函数275a` 内的全屏搜索变量 `zbx1/zby1/zbx2/zby2 = 26, 23, 290, 1279`。
- 本项目是**横屏 1280x720**：`TiledYoloDetection.kt` 断言 `width == 1280 && height == 720`，
  现有 schema 也存在 `(0, 0, 1280, 720)` 这种整屏区域。
- 因此两边差异**不止"点与点之间的分隔符"**，还差一次 90° 旋转。直接照搬数字会让每个搜索区域和偏移点都落到错误位置。

### 11.3 经像素级验证得出的坐标映射

```text
区域： (x1, y1, x2, y2) -> (y1, 719-x2, y2, 719-x1)   # 转换后取 min/max 并 clamp 到 1280x720
偏移点： (dx, dy) -> (dy, -dx)
```

验证依据（缺一不可，三条互相独立）：

1. **像素命中**：`函数275a` 的「主村庄 / 主进攻按钮」特征（主色 `a2d4eb`，9 个偏移点）按上式转换后，
   在真实横屏截图 `cocfz-apk-test/游戏截图/coc_clean.png` 的 `(45, 632)` 命中；该坐标正好落在左下角
   「进攻！」橙色按钮内，与源项目自带标定脚本 `游戏截图/analyze_calib.py` 输出的左下橙色按钮
   `bbox x:0-220, y:540-720` 完全吻合。
2. **命名自洽**：「左下角回营」`(26,23,178,178)` 转换后为左下角 `(23,541)-(178,693)`；
   「都城界面」（都城飞艇入口）用的是同一特征，同样落在左下角。
3. **排除其它候选**：另外三种候选映射（反向 90° 旋转、两种镜像）在同样条件下命中数为 0；
   其中镜像映射在物理上也不可能（真实屏幕不会左右翻转），故 90° 旋转变换是唯一解。

### 11.3b 颜色 hex 书写序（BGR）与特征迁移核对清单（2026-09-23 补）

从源脚本迁移/重采颜色特征时，以下四条必须逐一核对（本次都城入口 `4D6EFF` 调试中全部踩过）：

1. **hex 书写序是 BGR，不是 RGB**。
   `ColorSchema.parse` / 工具侧 `game_state.hex_arr` 都把 hex 按**书写顺序逐字节**与 cv2 读入的
   `(B, G, R)` 通道比较（与 App 生产特征一致）。因此：
   - 从截图取像素后想写成 hex：`'%02X%02X%02X' % (b, g, r)`（注意不是 r,g,b）；
   - 反过来，手里有一个 RGB 序的 hex（如 `FF794E`），要先反转成 `4E79FF` 再写入特征。
   误用 RGB 序时表现：主色/偏移点**全图零命中且毫无规律**（R/B 通道差恰好颠倒）。
2. **源脚本 findMultiColor 的 hex 可原样照抄**：源脚本与本项目口径相同（同为 BGR 书写序），
   不需要反转；带 `-101010` 后缀的，`ColorSchema.parse` 会忽略该后缀（工具侧解析正则需单独兼容）。
3. **偏移点方向**：`函数319a` 的偏移串是 `dx|dy|hex`，按 11.3 映射成 `(dy, -dx)` 后才是横屏偏移；
   手工转录时极易把 `(dy,-dx)` 写成 `(dx,dy)` 或漏掉负号 —— 迁移后务必先在截图上跑一遍
   `find_first` 验证命中位置是否落在目标物体上。
4. **动效目标慎用多点严格匹配**：都城飞艇（气球浮动 + 云层飘过）实测 9 点特征会整帧失配，
   需要剔除不稳定点（见 `下兵逻辑优化方案20260921.md` §八 M4-③）；
   更稳的兜底是"窗口内橙色像素计数"这类区域统计（正例 852~2979 / 反例 ≤590）。
   另外逐点匹配对**镜头缩放态**敏感，源脚本的前置定位手势（`zoomToCapitalShore`）是匹配成立的前提。

### 11.5 优化项 3（点阵字库 OCR 兜底）进展

- **字库格式实测修正**：文件头注释写的 `"字符|宽,高|..."` 是错的，实测是 **`字符|高,宽|64进制点阵串`**。
  依据：`TURING.Lib_LoadBase64` + `TURING.OCR` 的比较循环（`for w = 1..LibW { for h = 1..LibH { ... LibZ = w*LibH+1 } }`）
  说明 size[1] 对应"外层次数"、size[2] 对应"内层次数"，而位流是**行优先、高位在前**；
  按 (宽,高) 解释时字形呈斜切噪声，按 (高,宽) 解释时 `0/1/7/8//` 都能还原成清晰字形。
  另外原文还做了 `string.sub(lib, len - 高*宽 + 1)`，即**只取末 高*宽 个 bit**（前面是填充）。
- **已落地**：`tools/generate_pixel_font.py` → `PixelFontDigits.kt`（1891 条，68KB，内嵌常量）；
  `PixelFontOcr.kt`（二值化 → 8 邻域连通域 → 按行分组 → 与字库逐位比对取最高分）。已编译通过。
- **自测**：把字库字形回灌成合成图再 OCR，`1872155` / `8/12` / `5278190` / `0` 全部 100% 命中（算法本身正确）。
- **现版本实测（重要）**：在 `coc_clean.png` 金币行（真值 `1872155`）上，二值化 200-255 时
  单个字符最佳相似度只有 0.66~0.81，识别结果 `18351221`，**约 40~50% 正确**。

**文字"上下半截背景不同"的处理与实测（用户提供的局部截图）**

问题：资源数字是**白字黑描边**，压在**彩色渐变条**上（上半天是亮色条、下半天是深色条/条外背景），
背景不同会不会影响识别？

处理方式：判据只看**文字本身**（亮度≥200 且饱和度≤50），与背景无关——
- 彩条（金/紫/绿/黑）饱和度都很高 → 不算笔画；
- 黑描边亮度低 → 不算笔画，只取白色字芯；
- 因此"上下半截背景不同"不影响，只要背景不是"又亮又无彩色"（如纯白 UI）即可。

实测（该局部截图三行真值 `24 383 500` / `27 438 355` / `460 000`）：

| 判据 | 金币行 | 圣水行 | 黑油行 |
|------|--------|--------|--------|
| 纯亮度 ≥200 | **`?24383500?`** ❌ | `27438355` ✅ | `460000` ✅ |
| 亮度≥200 且 饱和度≤50（当前） | `24383500` ✅ | `27438355` ✅ | `460000` ✅ |

纯亮度会在**金币条高光边缘**多出 2 个连通块（8 位变 10 块）；加低饱和约束后 **22/22 位全对**，
且单字相似度 0.99–1.0（远高于 0.75 阈值）。

**分隔符条目修复**：此前脚本里"手写"的 `'.'`/`'/'` 条目位数不足（如 `/|13,8|…` 仅 90 bit，
需 104 bit），`PixelFontOcr` 会因 `raw.length < needed` **静默跳过** → `8/12` 这类计数会读不了。
已改为从老字库源文件复制的 **84 条合法条目**，并把它们纳入留出验证的候选集，
确认**不会抢走数字**（数字仍 100%）。当前字库共 **59 条数字 + 84 条分隔符 = 143 条**。

**能力边界与实测（设置页截图 `主世界-设置页2/4`）**

1. **`PixelFontOcr` 只认数字**（库内仅 0-9、`.`、`/`）。设置页的**中文**（设置/退出登录/更多设置/
   腾讯客服/…）它**完全不能识别**，那属于 `TextRecognizer`（ML Kit 中文 OCR）的职责。
2. **弹窗打开时背景会被压暗**（重要限制）：实测设置弹窗把背景资源条压到灰度 ~100–190，
   远低于默认 `grayMin=200`，此时 `PixelFontOcr` **一行都识别不出**。
   逐级下调阈值实测（真值 `26 200 000 / 20 971 227 / 446 200 / 10 352 / 0`）：

   | grayMin | 识别结果 | 说明 |
   |---------|---------|------|
   | 200 / 180 / 160 | 无 | 压暗后文字不到阈值 |
   | 140 / 120 | 部分 | 主数字开始出现，仍有 `?` |
   | 100 | `26200000`、`20971227`、`446200`、`910352`、… | 主资源数字读对，但**弹窗自身亮色 UI 混入**产生假行/假前导位 |

3. **结论**：`PixelFontOcr` 适用于**无弹窗的 HUD**（资源条/兵力数字，已验证 100%）；
   **弹窗打开时不要用它**读背景数字（要么等弹窗关闭，要么按"是否变暗"自适应下调阈值 +
   限定搜索区域排除弹窗）。中文界面文字一律走 `TextRecognizer`。

4. 附件说明：用户提供的设置页图为 **1080×608**（1280×720 被等比缩放的副本），
   测试时已还原到 1280×720；这也提示**外部传入的截图可能不是 1280×720**，接入前需确认/归一化。

### 11.15 活动内容（兵 / 法术 / 攻城器）全面解耦（2026-09-21）

**现象**：活动内容（活动兵、**活动法术**、活动攻城器）都是动态的——名称、数量随赛季变化，且**固定排在最左侧**，
会把原有内容整体右移、必要时多出一页（攻城器 9 种已实测跨 2 页）。

**处理**：`TrainTroops.kt` 统一为"可选配置表 + 按特征定位"：

| 类别 | 固定表 | 活动表（默认空，`emptyMap()`） | 计划构造方式 |
|------|--------|------------------------------|-------------|
| 兵种 | `TRAIN_CARD`（27） | `EVENT_TROOP_CARDS` / `EVENT_TROOP_COUNTS` | 识别结果 ∩ 表；识别结果全是未知项时回退 `CORE_FALLBACK` |
| 法术 | `SPELL_CARD`（18） | `EVENT_SPELL_CARDS` / `EVENT_SPELL_COUNTS` | `SPELL_CARD + EVENT_SPELL_CARDS`，次数取 `SPELL_COUNTS` / `EVENT_SPELL_COUNTS`（默认 0＝不造） |
| 攻城器 | `SIEGE_CARD`（9） | `EVENT_SIEGE_CARDS` / `EVENT_SIEGE_COUNTS` | `SIEGE_CARD + EVENT_SIEGE_CARDS`，默认每种 1 个 |

**为什么活动内容不会影响原有内容**：三者都是"**每条用自己的训练卡片特征跨页查找**"，
不依赖绝对位置、也不依赖顺序；活动内容出现在最左侧（哪怕名称/数量完全不认识）时，
它只是占位并让后续内容右移，原有条目照旧被找到（页数自适应：`MAX_PICKER_PAGES` + 连续空页提前结束）。
未知名称只会被**跳过**（绝不误点其它卡片），最后以日志列出"未找到"。

**验证**：兵种 27/27、法术 18/18、攻城器 9/9 都是在该机制下真机命中的（见 11.14）；
其中兵种页最左侧确实存在活动兵卡片（fire-skeleton 类），原有 14 + 13 个兵种仍全部命中，
即为"活动内容不影响原有内容"的直接证据。

### 11.17 卡在练兵界面不进搜索：根因是"选择英雄"弹窗的黑色遮罩（2026-09-21）

**现象**：App 连续两轮都停在练兵界面（"我的军队"页），**没有点右下绿色「进攻！」、没有进入搜索**。
用户第一反应是"是不是没识别到进攻按钮"——**不是**。

**排查结论（先排除识别问题）**：

- 用与 App **完全同一份特征定义**离线复核（`MainBaseAttackColors.AttackButton`，区域 `(1045,624)-(1245,662)`，
  主色 `9BFDCF`）；App 的 `ColorSchema.parse` 把 `similarity 0.9` 换算成 **`threshold = (255 × 0.1).toInt() = 25`**，
  与 Rust `is_color_match`（逐通道 `abs(p - t) <= threshold`）以及 `tools/game_state.py` 的 `TH = 25` **完全等价**，
  所以离线复核结果可直接代表 App 行为。
- 在"我的军队"页面上，`AttackButton` **命中 `(1056,629)`** → 特征本身没问题。
- 但同一页面在弹窗出现时命中为 `None`。采样右下按钮区域像素：`277450 / 256A48 / 497D64`（mean ≈ `[41,72,65]`），
  即亮绿 `9BFDCF` 被压暗成暗绿 → **差值远超 25，匹配必然失败**。

**根因**：`TrainTroops.kt` 收尾处**无条件** `TouchActions.tap(219, 139)` 关闭选兵面板。
当面板已经关闭时，`(219,139)` 在"我的军队"页正好落在**左侧英雄头像**上 → 误触弹出**"选择英雄"对话框**；
该对话框会给整个界面加一层**黑色遮罩**，遮罩下所有按钮颜色都被压暗 → **之后所有颜色特征全部匹配失败**，
脚本就停在这一屏一动不动。因此表现成"业务卡在练兵界面"，看起来像是"进攻按钮没被识别"。

**关键验证**：在该弹窗存在时发送返回键（`input keyevent 4`）→ 弹窗关闭、遮罩消失，
`AttackButton` **立刻恢复命中 `(1056,629)`**（同一条链路，仅此一步之差）。

**修复（3 处，已 `:app:compileDebugKotlin` 通过）**：

1. 新增 `closePickerIfOpen()`：把 `TrainTroops.kt` 里三处 `tap(219, 139)` 改为
   **仅在 `MyColors.TrainBarbarian` 命中（选兵面板确实打开）时才点** —— 从源头消除误触英雄头像。
2. `searchOpponentsAndDeployTroops()` **每轮开头先 `sweepBlockingPopups()`**：
   掉线弹窗 / 红叉 / 通用对话框在有遮罩时也点不中，必须先清弹窗再做特征匹配。
3. **未知弹窗兜底**：主村庄 `TrainTroops` / 联机模式页 `SearchOpponents` / 练兵页 `AttackButton`
   三个锚点**一个都没命中**（且不在对战页），说明被"既没有红叉、也不是通用对话框"的弹窗挡住
   （`sweepBlockingPopups()` 认不出"选择英雄"）→ 用返回键关掉再继续，避免空转直到搜索超时。
   实现：`private fun pressBack() { runCatching { Shell.cmd("input keyevent 4").exec() } }`（root shell，失败静默）。
